# Empório da Música AI Agent

AI-powered customer service prototype developed for the **Artefact AI Engineer Technical Challenge**.

The application simulates a virtual assistant for **Empório da Música**, a fictional musical instrument store located in Campo Grande, Brazil.

The agent can answer customer questions using structured business data and internal store policies while deciding when external tools are required.

---

## Overview

The main goal of this project is to demonstrate how a Large Language Model can interact with structured and unstructured business data in a controlled and explainable way.

The assistant can:

- Search products by name or keywords
- Filter products by category and maximum price
- Check product availability and stock
- Retrieve active promotions
- Check order information after customer verification
- Answer questions about store policies
- Answer questions about opening hours and payment methods
- Handle return and exchange policy questions
- Reject questions outside the store context
- Maintain conversation context during the current session

The project prioritizes **simplicity, reliability, explainability and separation of responsibilities** instead of introducing unnecessary infrastructure.

---

## Architecture

The solution follows a hybrid architecture combining:

- **LLM**
- **Function Calling / Tool Calling**
- **Structured CSV queries**
- **Lightweight document retrieval**
- **Prompt-based behavioral constraints**

High-level flow:

```text
Customer message
       |
       v
      LLM
       |
       | decides whether external information is required
       |
       +------------------------+
       |                        |
       v                        v
Structured Tools         Policy Retrieval
       |                        |
       v                        v
     CSVs              Store Policy PDF
       |                        |
       +-----------+------------+
                   |
                   v
            Retrieved context
                   |
                   v
                  LLM
                   |
                   v
          Final customer response
```

The LLM is responsible for understanding the customer request and deciding which tool should be called.

Business facts such as prices, inventory, promotions and order information are not generated by the model. They are retrieved from the provided data sources.

## Structured Data Tools

The agent currently exposes three main tools for structured data.

### `search_products`

Searches the catalog using optional filters such as:

- Product name or keywords
- Category
- Maximum price
- Availability

Example conceptual call:

```python
search_products(
    category="Violões",
    max_price=1000,
    only_available=True,
)
```

A product is considered available only when:

```text
stock_quantity > 0
AND
status == "active"
```

This distinction is intentional because the provided dataset may contain products with remaining inventory whose business status is not active.

---

### `get_active_promotions`

Retrieves active promotions and joins promotion data with product information.

The tool also calculates the discounted price deterministically in Python rather than asking the LLM to calculate it.

Only promotions associated with active products that have available stock are returned.

---

### `get_order_status`

Retrieves order information using:

- `order_id`
- `customer_email`

Both values are required.

The email must match the customer associated with the requested order before order information is returned.

If verification fails, the function returns a generic error instead of revealing whether the order exists.

This was implemented as a small **privacy-by-design** measure to reduce the risk of exposing customer information by simply enumerating order IDs.

## Policy Retrieval Strategy

Store policies are handled separately from structured operational data.

The PDF is:

1. Loaded with PyPDF
2. Converted to text
3. Cleaned to remove excessive whitespace
4. Divided into overlapping text chunks
5. Ranked against the customer question
6. Relevant chunks are returned to the LLM

The current implementation uses approximately:

```text
Chunk size: 1200 characters
Overlap: 200 characters
```

The overlap reduces the chance of separating an important policy rule across two chunks.

### Why a lightweight retrieval strategy?

The policy document contains only a small number of pages.

For this prototype, introducing:

- A vector database
- Embedding infrastructure
- External indexing services

would add complexity without providing a proportional benefit.

Instead, the system uses lightweight keyword-based retrieval.

This keeps the architecture simple while preserving the main RAG principle:

```text
Question
   |
   v
Retrieve relevant context
   |
   v
Add context to the LLM interaction
   |
   v
Generate grounded answer
```

For a larger production knowledge base, semantic embeddings and a vector database would be a natural evolution.

## Function Calling

The model receives descriptions of the available Python tools.

For example, when a customer asks:

```text
Quanto custa o Takamine GD20?
```

the model can decide to call:

```text
search_products
```

with the appropriate arguments.

The execution flow is:

```text
User
 |
 v
LLM
 |
 | requests tool
 v
Python tool
 |
 | queries business data
 v
Tool result
 |
 v
LLM
 |
 v
Natural-language response
```

The model does not execute Python functions directly.

It requests a tool call, the application executes the corresponding function, and the result is sent back to the model.

A maximum number of tool-call iterations is also enforced to avoid uncontrolled loops.

## Prompt Strategy

The system prompt defines both the assistant persona and important behavioral rules.

The assistant should behave as a helpful employee of Empório da Música:

- Friendly
- Informal
- Professional
- Familiar with musical instruments
- Objective

The prompt also establishes grounding rules.

The assistant is instructed to:

- Never invent prices
- Never invent inventory
- Never invent promotions
- Never invent order information
- Never invent store policies
- Use tools whenever business data is required
- Ask for customer verification before revealing order information
- Explicitly say when information cannot be confirmed
- Avoid exposing implementation details to customers
- Refuse unrelated questions politely
- Avoid claiming capabilities that are not implemented

The prompt therefore acts as a behavioral layer, while factual business information remains grounded in the available tools.

## Security and Privacy Considerations

Some challenge datasets contain customer information.

For this reason:

- Raw challenge data is excluded from Git
- `.env` is excluded from Git
- API keys are never committed
- Order information requires email verification
- Failed order verification does not reveal whether an order ID exists
- The LLM receives only the information required to answer the current question

For a production system, stronger authentication and authorization would be required.

## Known Limitations

This project is intentionally a prototype.

Current limitations include:

### Lightweight policy retrieval

Policy retrieval is keyword-based rather than embedding-based.

This works for the small provided document but may perform poorly with:

- Synonyms
- Semantically similar questions
- Very large knowledge bases
- Complex multi-document retrieval

### In-memory CSV processing

CSV files are loaded using Pandas.

This is appropriate for the small challenge dataset but would not scale to a large production catalog.

A production version would likely use a relational database.

### Session-only conversation memory

Conversation history exists only while the CLI application is running.

Closing the program clears the conversation.

### No transactional actions

The assistant can retrieve information but cannot:

- Create orders
- Cancel orders
- Process payments
- Modify customer information
- Process returns

### Basic customer verification

Order access currently validates an order ID against an email address.

A production environment should use real customer authentication and authorization.

### LLM dependency

Natural-language responses depend on an external LLM provider and may vary slightly between executions.

## Design Decisions

### Why Python?

Python was required by the challenge and is also a strong choice for AI applications due to its ecosystem for:

- LLM integrations
- Data processing
- APIs
- Machine learning
- Testing

### Why Function Calling?

Structured business information such as prices and order status should be retrieved deterministically rather than generated by the LLM.

Function calling gives the model the flexibility to determine when information is needed while keeping the actual data access under application control.

### Why separate structured data and policy retrieval?

The two sources have different characteristics.

CSV data is structured and deterministic:

```text
price
stock
order status
promotion
```

The policy PDF contains natural-language rules:

```text
returns
payment conditions
opening hours
procedures
```

Using different retrieval strategies for each source keeps the architecture aligned with the nature of the data.

### Why no heavy agent framework?

The challenge can be solved using a small number of explicit tools.

Implementing the tool-calling loop directly makes the architecture:

- Easier to understand
- Easier to debug
- More transparent
- Easier to explain during a technical interview
